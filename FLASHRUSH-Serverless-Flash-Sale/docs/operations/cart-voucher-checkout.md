# Cart, HAUMON and checkout

## Behavior

`/cart` uses the existing authenticated DynamoDB cart, provider and header badge. It shows variants, current stock, prices, quantities, selection and a removal confirmation dialog. Selection and voucher code are retained per account in sessionStorage; cart contents remain on the server. `/cart/checkout` reviews the selected products, saved address, delivery, voucher and payment before creating orders. The guest `/checkout` flow is preserved.

The current delivery policy is standard delivery with no shipping fee and COD. These are server-defined order options, not integrations with a carrier or online payment gateway. This is the default used pending a different business policy.

HAUMON applies to the current Flash Sale prices of all selected eligible cart lines, excluding shipping. Minimum subtotal: VND 3,600,000. Discount: 3,636 basis points (36.36%), rounded down to whole VND, with no maximum discount or usage limit specified. Example: VND 3,600,000 subtotal gives VND 1,308,960 discount and VND 2,291,040 payable.

## API and persistence

- `GET /me/checkout-quote`: server-supported delivery/payment options and voucher policy.
- `POST /me/checkout-quote`: accepts cart version, selected line IDs, voucher code and method IDs; checks ownership, stock, current prices and active campaigns before returning subtotal, discount, shipping fee, total and quantity. It does not reserve stock or create an order.
- `POST /me/checkouts`: additionally accepts `voucherCode`, `shippingMethod`, `paymentMethod` and `expectedTotal`. The server recalculates the quote; a stale/forged total is rejected. Existing clients without a voucher retain the previous request contract.

The checkout stores a pricing snapshot. Discount is allocated across child orders using cumulative proportional rounding, so all child totals add up exactly to the group total. The worker revalidates pricing and stock before the existing atomic transaction. Idempotent retries use the exact same saved request/key. Order views and admin revenue use the discounted total; legacy orders still use unit price times quantity.

Two additional JWT-protected API Gateway routes are generated by the existing CloudFormation extension. No new table, authentication provider or backend service is introduced.

## Validation

- Frontend: 64 tests; lint, typecheck and build passed.
- Backend: 43 tests; includes threshold edges, selected-lines-only qualification, cross-owner rejection, quote with no inventory reservation, forged totals/methods, rounding/allocation, replay, post-acceptance validation and net revenue.
- Deployment: 8 tests; operations: 1 test.
- Browser integration: registration/login, address, add/remove/cancel removal, quantity, selection, badge, reload persistence, voucher, checkout, confirmed child orders, history and password change. Viewports: 1440, 768 and 390 pixels, without horizontal overflow or JavaScript errors.

Browser integration runs actual application services and Lambda handlers against isolated Moto AWS services on ports 5174/8877. These are test fixtures, not a mock fallback in the production purchase flow. The new voucher flow has not yet been verified on deployed AWS.

## Deployment caveat

The existing main workflow targets `flashrush-manual` and its older API/CloudFront URL, without customer Cognito configuration. It does not deploy the CloudFormation extension for `flashrush-lab`, used by local port 5173 and the current customer site. A successful push/workflow therefore does not activate these new routes in lab. Do not change local configuration to point to the emulator for normal shopping.

For lab activation, use the existing guarded deployment command with the current admin secret and `--profile flashrush --region us-east-1`, wait for stack completion, then publish using stack outputs as described in [customer commerce](customer-commerce.md). Keep existing products, campaigns, accounts and orders. Deployment requires the intended environment to be confirmed; this change does not silently redirect CI or grant new IAM permissions.

## Manual verification after backend deployment

1. Sign in and add products from active Flash Sale campaigns. Open `/cart`, change quantity and reload; confirm the cart and header quantity agree.
2. Select products totaling less than VND 3,600,000. Apply HAUMON: show the minimum-spend error and prevent checkout with that invalid code. Remove the code to continue without it.
3. Select qualifying products; apply HAUMON and compare the server quote with the formula above. Unselect an item and verify eligibility/total is recalculated.
4. Cancel a removal, then confirm it; verify cart contents and badge. Try a sold-out line: it must not be purchasable.
5. Click Mua hang, choose a saved address, review standard delivery/COD and the final total, then confirm once. Check the group and individual orders for matching net totals.
6. Repeat at desktop/tablet/mobile sizes. Verify another account cannot see the first account's cart or orders. Do not use real purchases merely to test concurrency.
